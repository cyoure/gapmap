# ADR-0002 LLM 출력은 스키마로 강제하고, 원문에 없는 값은 버린다

## 배경
공고에서 `{company, required[], preferred[], deadline}`을 뽑아야 한다. 자유 텍스트로 받아서 정규식으로 파싱하면 모델이 형식을 조금만 바꿔도 깨진다.
그리고 형식이 맞더라도 **내용을 지어낼 수 있다.** 실제로 기술 스택이 적혀 있지 않은 공고에서 3b 모델이 `Java`를 필수 기술로 만들어 넣었다. 마침 이력서에 Java가 있어서 **매칭 점수가 100점**으로 나왔다.

## 결정
1. **형식**: Ollama의 `format`에 Pydantic 모델의 JSON Schema를 넘겨서 출력 형식 자체를 제한하고, 받은 결과를 Pydantic으로 다시 검증한다. 실패하면 최대 2회 재시도하고, 그래도 안 되면 502를 돌려준다 (`api/app/jobs/extract.py`).
2. **내용**: 추출한 값이 공고 원문에 정말 있는지 함수로 확인한다.
   - 마감일: LLM은 원문 문구(`deadline_raw`)만 뽑고, 날짜 계산은 `parse_deadline` 함수가 한다. 원문에 없는 문구면 버린다.
   - 기술명: 원문 표기 · 정규화된 이름 · 동의어(`skills.yaml`) 중 하나라도 원문에 나오지 않으면 버린다.
3. **정규화**: 기술명은 `skills.yaml` 사전을 먼저 본다 (`Spring Boot = 스프링부트 = SpringBoot`). 사전에 없으면 Chroma `skills` 컬렉션에서 임베딩 유사도로 가장 가까운 기술을 찾는다.
   - 기준값 0.75: 실제로 측정해 보니 관계없는 기술의 최고값이 0.663(Excel), 올바른 매칭의 최저값이 0.751(Kafka Streams)이었다. 그 사이로 정했다.

## 결과
- 👍 실제 공고를 여러 번 넣어도 JSON 형식이 매번 같다.
- 👍 "지어낸 기술 때문에 점수가 부풀려지는" 문제가 사라졌다.
- 👎 반대로 원문에 있는데 모델이 못 뽑는 누락은 막지 못한다 (예: "Kubernetes 운영 경험"). 검증으로 **틀린 값은 걸러낼 수 있지만, 빠진 값을 찾아 주지는 못한다.**
